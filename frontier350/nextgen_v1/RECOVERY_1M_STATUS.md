# Neral: <=1,000,000-token recovery contract (2026-09-16)

**Status: opt-in experimental implementation, NOT approved for full-model production or an unattended 2–3B-token run.** No training is started by these files. SAFE source on C: and verified separate vault copy on D: must remain untouched. Only own trusted model weights and native tokenizer; no weights/corpus uploaded to GitHub.

## Precisely what the constraint means

At every completed optimizer update, there must be a fully restorable checkpoint that is no more than 1,000,000 *processed training tokens* behind the current update. A restorable checkpoint includes all model weights, optimizer moments, LR/schedule counters, CPU/CUDA RNG, sampler RNG, data/tokenizer/architecture identities and step/token counters. If any required state, SHA receipt, free disk, atomic replacement or recovery validation fails: **stop instead of silently rewinding farther or resetting optimizer**. A catastrophic failure of all local storage, in-place tampering of shared hard-link inodes, and GPU errors between verification boundaries cannot be made impossible; an independent external backup is still necessary.

Native whole-model default shape `seq=512`, `microbatch=4`, `grad_accum=8` = **16,384 tokens/optimizer step**. The opt-in wrapper overrides native `--save-every=100` (=1,638,400 tokens, unacceptable) to **61 steps = 999,424 tokens** maximum. Larger update shapes are rejected if one update itself exceeds 1M; the checkpoint period is recalculated from actual caller parameters. V9 four-block trainer instead has 24,576 tokens/update and normally writes `resume.pt` each 20 updates (=491,520 tokens), but it **does not yet use this journal**: its overwriting checkpoint is not sufficient proof of disaster recovery.

## Actual implementation

- `checkpoint_journal.py`: SHA-256 receipt, complete-state and monotonic gap contracts, atomic receipt, immutable archived generations from same-volume hard links, explicit read-only verification and restore to a **new** filename. Each generation is kept; the `retain` parameter is only a minimum validation rule, NOT an implemented disk cleanup mechanism. Never claim space is bounded or allow an unlimited run without an independently reviewed retention/storage policy.
- `train_full_with_journal.py`: opt-in native whole-model wrapper only; requires source SHA, trusted local origin, native schema 2, full optimizer and RNG/sampler state; refuses V9-only optimizer continuity, routes native full-state saves to journal and skips the trainer's duplicate terminal save. It does not modify legacy trainer defaults or auto-promote any model.
- Existing verified separate C: -> D: SAFE backup remains a *separate copy*. Journal hard links share the same disk and file bytes and are **not** another drive or independent backup. Hard links avoid writing another several-GB model *copy* for each generation but native checkpoint serialization, disk writes and SHA reads are still expensive. Do not report measured throughput improvements without a real, multi-GB timed experiment.

## Evidence and limitations

- Offline CPU tests: [155 passed](https://github.com/Cola968/neral-helios/actions/runs/35114616334), including before/after-atomic-replace crash cases, tampered SHA, missing optimizer/sampler, non-overwriting restore, automatic <=1M interval, duplicate final save. They are synthetic software tests, not full-model CUDA execution.
- The [one-shot actual Windows/WSL D: filesystem run](https://github.com/Cola968/neral-helios/actions/runs/35114970232) passed using a **tiny synthetic Torch model and optimizer**: retained old checkpoint, checkpoint interval 999,424, injected crash after replacement but before latest receipt, recovered last committed state to a new file, deserialized it and verified counters. It did NOT read Neral weights or train on GPU.
- Earlier deterministic short V9 GPU restart gate passed only for 4 trainable blocks; previous 20-step candidate showed NIS2 chat regression and later conservative candidate did not demonstrate a convincing improvement. Independent FP32 holdout difference is negligible. No quality promotion.

## Hard blockers before claiming safe fast full-model training

1. **Checkpoint compatibility:** current protected SAFE/V9 checkpoints keep a *four-block optimizer* under `v9_training_state` and an empty/native-incompatible root optimizer. An exact native whole-model continuation is IMPOSSIBLE from that state by relabeling it. Develop a separate explicit new-optimizer warm-start protocol if necessary, without rewriting the SAFE checkpoint; mark resulting run as a new optimizer lineage and benchmark it independently.
2. **VRAM and true speed:** verify full 349,825,152-parameter BF16 forward/backward plus AdamW moments and checkpoint writes on the local RTX 4070; tune gradient accumulation, activation checkpointing and `torch.compile` only with measured end-to-end time. The historical ~25–28k token/s figures apply to the 4-block optimizer step, not full-model end-to-end quality-accepted training. 44k token/s not proven.
3. **Real recovery:** use a *short, bounded, isolated* full-model job with actual multi-GB checkpoint; crash deliberately at controlled boundaries and show restored model/optimizer/RNG/data order & exact next-update reproduction. Do not start billions of tokens without this.
4. **Disk capacity:** journal currently retains every generation (no deletion). A 2–3B-token run would accumulate thousands of multi-GB generations; implement and test a reviewed, conservative retention policy and verify free capacity before launch, while keeping protected milestones and the independent SAFE backup. Do not lower SHA checks or erase user files to force continuation.
5. **Quality:** independent validation, actual answer generation/EOS, NIS2 with held-out contamination safeguards, math/code/DE/EN and no regression must precede promotion. Faster training alone is not successful training.
